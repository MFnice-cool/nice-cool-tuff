# UI Perf & Visual Consistency / Оптимизация UI и визуальная согласованность

Комплексный бэклог по трём проблемам лаунчер-IDE: лаги/баги на слабых
машинах, отсутствие адаптации под разные типы пользователей, визуальная
несогласованность (кривые углы, переполнение текста, нагромождения).

Дата начала: 2026-07-30.

## Фаза 0 — авто-детект слабого ПК

`src/lib/store.ts` → `detectWeakHardware()`: проверяет
`navigator.hardwareConcurrency <= 2` или `navigator.deviceMemory <= 2`.
Разовая проверка в `App.svelte` (`applyPerfAutoDetect`, флаг
`perfAutoDetected` в `LauncherSettings` / `launcher_settings.rs`) — включает
`potato-pc` режим (reduced motion) один раз при первом запуске на слабой
машине и больше никогда не переопределяет выбор пользователя из Settings.

## Фаза 1 — производительность

- Все тяжёлые вьюхи (`IdeWorkspace`, `Mods`, `Graph`, `World`, `Diagnostics`,
  `ConfigEditor`, `Settings`, `RecipeBrowser`, `QuestEditor`, `Library`,
  `Chats`, `Me` и др.) переведены на `import()` через `VIEW_LOADERS` в
  `App.svelte` вместо статических импортов — грузятся только при открытии.
  Стартовый бандл (эквивалент "загружаем всё сразу") сократился на ~77-80%
  JS / ~74-77% CSS (gzip).
- `ViewLoading.svelte` — скелетон-заглушка на время подгрузки чанка.
- `setInterval`/`requestAnimationFrame` во всех компонентах проверены — рабочие
  циклы либо самоостанавливаются (d3-force в `Graph.svelte`), либо гасятся в
  `onDestroy`, либо защищены флагом `drawScheduled` (`WorldMap.svelte`).
- Отложено: разбиение монолитов `Mods.svelte`/`Graph.svelte`/`Diagnostics.svelte`
  на подкомпоненты — большой объём/риск, уже не критично для perf после
  lazy-loading (эффект был бы в основном для maintainability, не для скорости).

## Фаза 3 — визуальная согласованность

- **Токенизация `border-radius`**: 143 хардкод-значения, точно совпадающих с
  токенами (`--border-radius-sm/md/lg/xl` = 8/12/16/24px), заменены на
  `var(--border-radius-*)` в 36 компонентах. Это zero-visual-diff в обычной
  теме, но чинит "острые" темы (win95, pixelato, aether, frost) и
  тумблер "sharp corners" — раньше хардкод не реагировал на них, оставляя
  визуально выбивающиеся скруглённые углы.
  - Значения без точного токена (2-6px декоративные акценты; 10/14/18/20/22px
    "почти токен") намеренно не тронуты — их замена меняет реальный размер
    скругления и требует визуального ревью, а не механической замены.
  - `SkinPreview3D.svelte:466` (`36px 36px 12px 12px`, составной shorthand) —
    не тронут, единственный такой случай в кодовой базе.
- **`.tb-truncate` / `.tb-truncate-2`** (`src/styles.css`) — переиспользуемые
  утилиты для одно-/двухстрочной обрезки текста вместо разрозненного
  копипаста `overflow:hidden; text-overflow:ellipsis; white-space:nowrap`.
- Заодно починены 4 предупреждения `svelte-check` "Also define the standard
  property 'line-clamp'" в `YoutubeFeed.svelte`, `ListingCardPreview.svelte`,
  `Library.svelte`.
- Отложено: нормализация padding/spacing по сетке 4/8px — требует
  визуального QA по всем экранам/темам, не механическая замена.

## Фаза 4 — регресс-контроль

Три guard-скрипта в `apps/tuffbox-desktop/scripts/`, вызываются одной
командой `npm run lint:perf` (или по отдельности `lint:tokens`,
`lint:lazy-views`, `lint:bundle-budget`) и подключены в CI
(`.github/workflows/build-windows.yml`, шаг "Frontend perf/style regression
guards", сразу после `npm run build`):

1. **`check-border-radius.mjs`** — не даёт снова захардкодить
   `8/12/16/24px` вместо токена (см. Фазу 3).
2. **`check-lazy-views.mjs`** — не даёт статически заимпортить вьюху,
   которая уже есть в `VIEW_LOADERS` (см. Фазу 1); такая ситуация тихо
   сводит на нет весь эффект lazy-loading, потому что бандлер всё равно
   зашьёт компонент и его зависимости (включая тяжёлые вроде
   `ConfigEditor`/`IdeWorkspace`/`skinview3d`) в стартовый чанк.
3. **`check-bundle-budget.mjs`** — после `npm run build` считает gzip-размер
   ровно тех файлов, которые `dist/index.html` подключает напрямую
   (`<script src>`, `<link rel="stylesheet">` — то есть гарантированно грузятся
   при каждом старте), и падает, если бюджет превышен:
   - JS: 230 KB gzip (базовая линия ~160 KB, запас на рост)
   - CSS: 30 KB gzip (базовая линия ~17 KB)

   При реальной необходимости раздвинуть бюджет — делать это осознанно,
   с комментарием-обоснованием в самом скрипте, а не молча поднимать число.

### Чек-лист визуального QA (ручной, перед релизом)

Автоматического visual regression (скриншот-диффинг по всем
темам/вьюхам) сейчас нет — это отдельная инвестиция (baseline-скриншоты +
Playwright-сьют). До тех пор — ручной прогон по этому чек-листу при
заметных UI-изменениях:

- [ ] Прогнать сборку (`npm run build`) и `npm run lint:perf` — 0 ошибок.
- [ ] Открыть каждую тему (`tuffbox`, `tuffbox-light`, win95-подобная
      острая тема, pixelato) и пройтись по Dashboard, Mods, Graph,
      Diagnostics, Settings — искать: обрезанные/наезжающие подписи,
      скруглённые углы там, где тема должна быть "острой", контраст текста.
- [ ] Переключить "sharp corners" в Settings → Appearance при активной
      светлой/тёмной теме — все панели/карточки/кнопки должны стать острыми
      (кроме намеренных pill-элементов: бейджи/чипы/аватары — см. комментарий
      "Pills / round avatars stay fully round" в `themes.css`).
- [ ] Включить `potato-pc` (reduced motion) вручную — анимации/transition
      должны исчезнуть, лейаут не должен "прыгать".
- [ ] Сузить окно до минимальной поддерживаемой ширины — проверить
      Sidebar/Header/карточки на переполнение/наложение текста.
- [ ] Заполнить списки длинными названиями (модпак/мод/файл с очень длинным
      именем) — убедиться, что применяется truncate, а не выход за рамки
      контейнера.
- [ ] Открыть каждую lazy-loaded вьюху с холодным стартом — убедиться, что
      `ViewLoading` скелетон показывается кратко и без "прыжка" лейаута при
      подмене на реальный контент.
